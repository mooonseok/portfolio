# 포트폴리오 팀 진행표

전역 `engineering-workflow`와 `references/development.md`,
`references/state.md`를 읽고 이 프로젝트의 역할·검사·합류 조건을 적용합니다.
전역 스킬이 없는 환경에서는 AGENTS.md §7과 아래 절차를 따릅니다. 메인 세션이
리드이며 작업 상태의 단일 작성자입니다.

## 역할과 소유권

| 담당            | 고치는 곳                                         | 책임                                                |
| --------------- | ------------------------------------------------- | --------------------------------------------------- |
| 리드            | 작업 지시, 공유 계약, 통합                        | 작업 분배, 상태 기록, 결과 합류, 최종 커밋          |
| data-builder    | dto, constants, content, lib(화면 외), api, tests | 타입·순수 함수·서버 데이터                          |
| ui-builder      | components, sections, styles, app 페이지          | 뷰·스타일                                           |
| scene-builder   | lib/orbit·opener·diorama, 관련 hooks              | three.js 장면, GSAP 타임라인                        |
| qa-runner       | 소스 변경 없음                                    | 전체 검사, 빌드, 3100 서버, 캡처·G2 측정, 자원 정리 |
| design-reviewer | 변경 없음                                         | 독립 G3·접근성 검토                                 |
| perf-auditor    | 변경 없음                                         | 준비된 빌드의 JS 예산·Lighthouse·3D 성능 측정       |
| copy-editor     | 변경 없음                                         | 문구·커밋 제목 검토                                 |
| docs-keeper     | README, HANDOFF, DESIGN.md                        | 실제 변경에 맞춘 문서 갱신                          |

## 실행 그래프

| 노드      | 입력과 산출물                                              | 통과 조건과 다음 노드                                    | 실패 시 이동                                 |
| --------- | ---------------------------------------------------------- | -------------------------------------------------------- | -------------------------------------------- |
| 작업 정의 | 요청 범위, 수용 조건, 소유 파일, 승인된 방향을 대화에 기록 | 담당·검사·완료 지점이 정해지면 계약 확정                 | 빠진 필수 결정만 사용자에게 확인             |
| 계약 확정 | 공유 타입·상수·토큰과 담당별 입출력                        | 한 담당이 계약을 작성하고 호출자가 사용할 수 있으면 구현 | 계약 작성 담당                               |
| 구현      | 고정 계약과 소유 목록 → 변경 파일·검사 결과                | 필요한 담당 모두 결과를 제출하면 통합                    | 해당 파일 소유 담당                          |
| 통합      | 담당별 결과와 현재 변경 상태                               | 계약 사용과 소유 범위를 확인하면 QA                      | 계약 오류는 계약 확정, 구현 오류는 소유 담당 |
| 검증      | 동일 코드 버전 → 검사·캡처·미해결 지적                     | 필수 검증과 필요한 독립 검토가 통과하면 문서 갱신        | 리드가 원인을 분류해 해당 노드로 반환        |
| 마무리    | 문서 변경까지 포함한 최종 상태                             | `pf-verify` 통과 후 리드가 `pf-commit` 실행              | 영향을 받은 검증·수정 노드                   |

- `design-only`는 시안 전달로 끝냅니다. `design-build`는 `pf-design`의 G4 뒤
  계약 확정으로 옵니다. 승인된 디자인의 `build`는 계약 확정부터 진행합니다.
  `fix`는 실패 재현과 수용 조건을 작업 정의에 넣고, `review`는 검토 결과를
  전달합니다. 요청에 구현이 포함될 때 해당 구현 경로를 이어갑니다.
- 독립적인 구현은 병렬로 맡기고 계약 작성은 먼저 끝냅니다. 같은 파일에 작성자를
  두 명 배정하지 않습니다. 계약 변경이 필요하면 리드에게 반환하고, 변경된 계약을
  사용하는 결과와 검증을 다시 확인합니다.
- Codex의 공유 checkout에서는 소유 파일을 분리합니다. 격리가 필요하면 사용 중인
  플랫폼의 worktree 기능으로 현재 작업 기준을 보존합니다. 담당은 변경을 제출하고
  리드가 통합합니다. 구현 담당은 빌드·서버 실행·커밋을 하지 않습니다.
- 지시서에는 승인된 요구사항, 소유 파일, 계약, 수용 조건, 실행 가능한 검사와
  산출물 버전을 담습니다. 다른 담당이 함께 작업 중임을 알리고 그 변경을
  보존합니다.

## 검증 자원과 수정 루프

1. QA가 산출물과 검증 모드를 식별하고 `pf-verify`를 실행합니다. 레포 밖 시안은
   `prototype`으로 원본 HTML·의존 자원을 확인하고 직접 열거나 로컬 정적 서버로
   제공합니다. 프로젝트 구현은 `project`로 §5 전체를 검사합니다. QA는 실제 검증
   대상의 경로·주소·버전·PID(서버가 없으면 없음)를 리드에게 전달하고, 다른
   검토자는 준비 신호 후 같은 대상을 확인합니다.
2. 기능·화면 검토와 독립 검토의 결과를 같은 버전으로 모읍니다. 성능 측정은 다른
   브라우저 부하가 없는 구간에 배정합니다. 리뷰어는 빌드하거나 서버를 재시작하지
   않습니다.
3. 지적에는 재현 조건, 근거, 파일 소유자, 해결 조건을 붙입니다. 검증 담당은
   실패를 리드에게 반환하고, 리드는 해당 담당을 재실행한 뒤 영향받은 검증으로
   돌아갑니다.
4. 같은 산출물과 수용 기준에 대한 최초 검토 이후 수정은 최대 2회입니다. Unslop,
   G3, 담당 교체로 횟수를 초기화하지 않습니다. 한도 뒤에도 남으면 시도·근거·남은
   문제를 전달하고 사용자 판단을 기다립니다.
5. 상태와 검증 근거는 전역 `references/state.md`의 레포 외부 작업 JSON에
   기록합니다. 전역 지침이 없으면 AGENTS.md §7의 최소 필드와 검증 모드를
   기록합니다. 한 버전에서 통과한 검사를 중복 실행하지 않고 입력이 바뀐 결과를
   무효화합니다. 프로젝트 변경의 최종 커밋 전에는 현재 버전의 AGENTS.md §5 전체
   통과가 필요합니다.
6. QA는 모든 검토자의 사용 완료를 확인한 뒤 서버·브라우저를 정리합니다. 실패나
   사용자 대기 경로에서도 직접 띄운 자원을 정리하고 PID·포트로 종료를
   확인합니다.
