# 포트폴리오 디자인 진행표

전역 `engineering-workflow`의 `references/design.md`와 `references/state.md`를
읽고 아래 프로젝트 관문을 적용합니다. 전역 스킬이 없는 환경에서는 AGENTS.md §7과
이 절차를 따릅니다. 먼저 `PRODUCT.md`, `DESIGN.md`, HANDOFF.md §4~6을 읽습니다.
화면 하나를 한 단위로 진행하며 시안·프로토타입은 레포 밖 Artifact로 보여 줍니다.

## 요청과 산출물

- `design-only`는 G4에서 확정한 시안과 근거를 전달합니다. `design-build`는 G4 뒤
  `pf-team`의 계약 확정으로 연결합니다. 이미 승인된 디자인의 구현은 그 계약에서
  시작하고 승인된 시안을 다시 고르지 않습니다.
- `review`는 현재 화면의 지적과 근거를 반환합니다. 수정 요청이 함께 있으면 승인
  범위에 맞는 개선 경로를 이어갑니다. 기존 화면의 큰 개편은 요구 카드 단계에서
  Unslop 진단을 먼저 사용해 발견한 문제를 시안에 반영할 수 있습니다.
- 입력은 화면 목적, 사용자, 승인된 방향, 금지 사항, 경로와 상태입니다. 산출물은
  시안 버전, 토큰·모션 사양, 캡처, G2 측정과 G3 결과입니다.
- 레포 밖 시안은 `pf-verify`의 `prototype` 모드로 QA가 원본 HTML·의존 자원을
  확인하고 브라우저에 준비합니다. QA의 실제 시안 주소·버전·준비 신호를 G2·G3에
  전달합니다. 프로젝트 구현 뒤에는 `project` 모드로 §5 전체와 화면 검증을
  실행합니다. 프로젝트 소스 변경이 없는 시안은 G4 전달까지 진행합니다.

## 실행 그래프

| 노드           | 작업과 산출물                                                                                        | 통과 조건과 다음 노드                   | 실패 시 이동                     |
| -------------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------- | -------------------------------- |
| 요구 카드      | `frontend-design`으로 목적·사용자·제약 정리                                                          | 확인된 요구를 레퍼런스 분석에 전달      | 빠진 필수 요구 확인              |
| 레퍼런스 분석  | 사용자 레퍼런스와 필요에 맞는 `design-taste-frontend`, `awesome-design-md`에서 구성·재질·움직임 비교 | 요구와 연결된 부품 방향 확보            | 요구 카드                        |
| G1 방향 선택   | 핵심 부품을 실제 화면 크기로 2~4개 비교                                                              | 사용자 선택 후 상태·타임시트 확정       | 부품 시안                        |
| 프로토타입     | 선택한 방향을 단일 HTML과 검증 훅으로 구현                                                           | 실제 화면에서 측정 가능하면 G2          | 프로토타입 담당                  |
| G2 기능 검증   | 폭·상태·회전 단계별 겹침과 조작 검사                                                                 | 필수 항목 통과 후 Unslop                | 결함을 해당 담당에게 반환        |
| Unslop 보완    | 진단 → 적용할 규칙 확정 → 필요한 순서별 보완                                                         | 변경이 있으면 영향받은 G2, 이후 독립 G3 | 구현 결함은 담당, 방향 변경은 G1 |
| G3 독립 검토   | 네 항목의 점수·근거와 필수 결함 목록                                                                 | 각 7점 이상이며 필수 결함이 없으면 G4   | 담당 수정 후 영향받은 G2·G3      |
| G4 사용자 확정 | 시안과 남은 제한을 함께 제시                                                                         | 요청 범위에 따라 전달 또는 구현         | 사용자 피드백이 영향받는 노드    |

G1 부품 시안은 행성·위성·테마처럼 화면의 핵심을 먼저 비교합니다. 데스크톱과 22px
안팎의 휴대폰 부품 크기를 함께 봅니다. 상태 사양은 기본·선택·호버·움직임
줄이기·3D 불가를 포함하고, 시간표는 `pf-motion`을 따릅니다. 프로토타입에는
`__settle`, `__seek`, `__phase`, `__hover`처럼 실제 장면 상태를 재현하는 훅과
측정 함수를 둡니다.

## G2 측정 조건

1440×900, 1280×800, 1024×768, 834×1112, 744×1024, 430×932, 390×844, 375×667,
360×740, 320×568, 844×390에서 확인합니다. 회전 장면은 32~64단계마다 이름표 겹침,
메뉴·패널과의 겹침, 화면 밖 넘침, 행성이 패널 밑으로 들어가는 경우를 셉니다.
모두 0이어야 합니다. 선택·터치·키보드와 움직임 줄이기 상태도 확인합니다.

## Unslop의 적용 범위

- 설치된 `unslop`을 읽고 실제 화면을 진단합니다. 사용자 승인 사양과 프로젝트
  토큰을 먼저 적용합니다. 70초 궤도 회전, 오프닝, 판화 재질 등 기존 결정과
  충돌하는 일반 규칙은 적용 대상에서 제외하고 이유를 기록합니다.
- 보완은 간격 → 색 → 아이콘 → 문구 → 글꼴 → 배치 → 세부 요소 → 시각 요소 → 모션
  순서로 필요한 항목에 적용합니다. 이미 승인된 범위 안에서는 진행하고, 새로운
  방향 선택이 필요할 때 사용자에게 진단과 제안을 보여 줍니다.
- 문제가 없으면 진단 결과를 G3로 넘깁니다. 수정이 있으면 변경
  파일·토큰·문구·모션이 영향받는 G2 결과를 무효화하고 다시 측정합니다.
- Unslop의 렌더 횟수 제한을 프로젝트 필수 폭·상태 검증의 생략 근거로 사용하지
  않습니다. Unslop과 독립 G3는 같은 산출물의 수정 횟수를 공유합니다.

## G3 평가 계약

`design-reviewer`에는 승인된 요구사항·제약·모션 사양, 화면 주소, 산출물 버전,
원본 경로, 검증 훅, 확인할 폭을 줍니다. 구현자의 자기평가를 제외하고 사용자의
선택을 평가 근거에 포함합니다. 각 항목은 0~10점과 화면 근거를 함께 반환합니다.

| 항목   | 관찰 기준                                                              |
| ------ | ---------------------------------------------------------------------- |
| 고유성 | 프로젝트의 주제와 핵심 시각 요소가 연결되고 승인된 콘셉트가 일관되는가 |
| 위계   | 첫 시선, 선택 상태, 설명, 행동의 우선순위를 구별할 수 있는가           |
| 디테일 | 정렬·간격·글꼴·테두리와 상태 표현이 여러 폭에서 일관되는가             |
| 움직임 | 승인된 타임시트와 조작 반응이 맞고 정지·대체 상태에서도 이해되는가     |

0~3점은 목적이나 요구를 충족하기 어려운 상태, 4~6점은 수정할 구체적 문제가 있는
상태, 7~8점은 요구를 충족하고 근거가 확인된 상태, 9~10점은 세부 완성도가 높은
상태로 평가합니다. 각 7점 이상과 별개로 조작 불가, 정보 가림, 접근성 위반, 승인
요구 위반은 필수 결함으로 남깁니다. 미확인 항목은 통과로 처리하지 않습니다.

같은 산출물·수용 기준의 최초 검토 후 수정은 최대 2회입니다. Unslop 재호출, 담당
교체, G2·G3 재진입으로 횟수를 초기화하지 않습니다. 한도 뒤에는 근거와 남은
문제를 사용자에게 전달합니다. 리드가 레포 외부 작업 JSON에 상태를 기록합니다.
전역 상태 지침이 없으면 AGENTS.md §7의 최소 필드와 검증 모드를 기록합니다.

## 구현 인계와 프로젝트 기준

- G4 뒤 실제 구현이 요청되었으면 토큰은 `impeccable`, 문구는 필요한 경우
  `copywriting`·`humanize-korean`으로 확정하고 `pf-team`·`pf-build`로
  인계합니다. 화면 문구는 `src/content`에 둡니다.
- 상태는 기호와 글자로 구별하고, 프로젝트는 무늬와 실루엣으로 구별합니다.
  강조색은 정해진 선택 위치에 한 가지를 사용합니다.
- 중요한 내용은 터치에서 볼 수 있어야 합니다. 첫 탭은 선택, 이동은 패널의 링크로
  제공합니다. 겹침은 빈자리로 옮겨 해결합니다.
- 제목의 한 단어만 다음 줄에 남지 않도록 `word-break: keep-all`을 적용합니다.
- 확인되지 않은 수치·임시 문구·과장은 사용하지 않습니다. 비공개 레포의 링크를
  숨기고 모의 운용을 실거래로 표현하지 않습니다.
- 보라 그라데이션 히어로, 전체 가운데 정렬, 모든 카드의 동일한 둥근
  모서리·그림자 같은 반복적인 AI풍 구성을 피합니다.
